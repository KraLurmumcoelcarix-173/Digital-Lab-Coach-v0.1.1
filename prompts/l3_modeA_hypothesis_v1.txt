resolved), plus `values` — that pin's ACTUAL value on the representative

actually drives the suspicious pin instead of a look-alike (e.g. WHICH of
four Consts feeds the adder's c_i). GATE-KIND SANITY CHECK: for every
suspect gate, compute what its element kind SHOULD output from its input

appear on a suspect:

STORED DATA (ROM / LookUpTable) — CHECK IT FIRST, NOT LAST: when a
suspect stores data, decide the DATA story before any wiring hypothesis.
The data signature is frozen outputs: the same found value in every
failing row (an empty ROM reads 0 everywhere), while the address/select
inputs resolve correctly in the values table. The wiring/logic signature
is the opposite: outputs that VARY with inputs in ways a mis-wired or
wrong-kind gate explains. In a circuit with both a ROM and logic gates,
sort the evidence into those two buckets first and fix the bucket the
failing rows actually show.
- A suspect ROM whose attrs say the data is EMPTY (`data_note`) is the
  prime suspect for frozen-at-0 rows: derive the FULL table and write
  it in ONE change_attribute op. Its suspect_wiring record carries two
  MACHINE-TRACED facts — treat them as ground truth over any tunnel or
  signal NAME (student names lie; a bus named like an input column is
  still just stored-word bits):
    `address_by_row`            which stored-word address each failing
                                row actually selects;
    `output_bit_map`            which stored-word bit position feeds
                                each named output ("RegWrite": "bit 7");
    `expected_outputs_by_row`   the machine-parsed expected value of
                                every output column per failing row —
                                use THESE numbers, never re-read the
                                raw row text.
    `address_input_drivers`     the selector computing the address
                                (e.g. a priority encoder): for each of
                                its input pins, the exact component
                                driving it ("Or[112]") and that pin's
                                value on the failing rows.
  Word for address k = set exactly the bits where
  expected_outputs_by_row of the row(s) mapping to k is 1, placed per
  output_bit_map. One word per address, nothing more.
- Stored words the student wrote themselves are checkable the same way:
  derive what each failing row's address SHOULD store and compare;
  change only words the evidence convicts, keep every word that passing
  rows rely on.
- WRONG ADDRESS beats wrong data: when `address_by_row` shows failing
  rows selecting an address whose stored word serves OTHER (passing)
  rows — or two failing rows demand DIFFERENT words at ONE address —
  the stored data is innocent and rewriting it would break the passing
  rows: the ADDRESS PATH is the bug. Read `address_input_drivers` to
  see which selector inputs assert on the failing rows and exactly
  which gate drives each one; a gate asserting on a row that should
  not select it is the culprit — use its literal component_index. If
  MORE THAN ONE input asserts at once, every wrongly-asserting gate is
  broken: fix them ALL in ONE ops list (the selector's priority hides
  the quieter wrong gates until the loudest is silenced).
- A [ROM NOTE] block below means every ROM in this circuit was checked
  word for word against the official contents registered for this lab
  before this run: those stored words are correct by definition — NEVER
  propose a Data change on a ROM (it is stripped before verification);
  the failing rows come from wiring, selects, or other components.
